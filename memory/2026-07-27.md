### Highest USER impact — 11 strings shipped untranslated on the revenue surface

- Audit claimed 5 paywall strings missing from the catalog; scanning myself found **11**
  (5 paywall + 6 AI insight fallbacks).
- Mechanism: `String(localized:)` returns the KEY when no catalog entry exists → pt-BR
  devices saw **English on the subscription paywall**. Violates the pt-BR contract.
- The localization suite could not catch it: ~35 assertions were `#expect(!localized.isEmpty)`,
  which is true for the returned key → **structurally incapable of failing**.
- Fixed: added all 11 with pt-BR translations + replaced the tautological tests with a
  **source-scanning test** that walks every `L10n.localized(...)` / `String(localized:)`
  literal and requires a catalog entry.
- **Two existing tests then failed — because the fix was correct.** `InsightServiceTests`
  asserted the English fragments `"safe summary"` / `"next week"`, which only passed
  *because the strings were untranslated*. The suite had encoded the bug as expected
  behavior. Fixed by asserting through `String(localized:)` (the same lookup production
  uses), so they verify the fallback path, not the language. Made `recommendation` stricter
  (`==` not `contains`).

## Staging/TestFlight attempt — what was fixed and what still blocks (2026-07-27, evening)

### ASC auth: the two planes, resolved for real this time

- `asc web auth login` authenticates a **web session only**. Enumerated the whole family to prove it:
  `auth, sandbox, apps, removed-apps, bundle-ids, privacy, review, subscriptions, analytics, xcode-cloud`.
  **There is no build-upload command in `asc web`.** No number of web logins will ever enable an upload.
- Publishing (`apps`, `builds`, `status`, `testflight`, `publish`) needs the **JWT/API plane** = `asc auth login`
  with Key ID + Issuer ID + `.p8`. `asc web auth` cannot mint an API key either (subcommands are only
  login/status/capabilities/logout) — Apple issues keys **only** through the ASC web UI. Hard circular
  dependency; the CLI cannot bootstrap itself.
- **USEFUL: the Issuer ID equals the `publicProviderId` returned by `asc web auth status`.**
  Here: `69a6de76-5827-47e3-e053-5b8c7c11a4d1`. Key registered: `5UP9Q47FW7` (in `~/Documents`).
- `asc auth login` **refuses a world-readable `.p8`**: "private key file is too permissive; run chmod 600".
  Fix the mode first, then register.
- **`~/.asc/config.json` `app_id` was WRONG**: it held `6780245377` = **Paquera AI**
  (`com.mneves.paquera-mobile`), not AIPedometer. AIPedometer is **`6778799265`**. Always pass `--app`
  explicitly; never trust the profile default, or the build lands on another app record.

### THE REAL BLOCKER (fixed, `af03e6b`) — watch app as a second top-level product

- `project.yml` had `SKIP_INSTALL: NO` on `AIPedometerWatch`, so an archive contained **two** apps under
  `Products/Applications` (AIPedometer.app AND AIPedometerWatch.app). Xcode then cannot identify a primary
  app, writes **no `ApplicationProperties`** into the archive `Info.plist`, and `xcodebuild -exportArchive`
  reports an **empty set of distribution methods** — surfacing as the baffling
  `error: exportArchive exportOptionsPlist error for key "method" expected one {} but found app-store-connect`.
- **`expected one {}` with empty braces means "no valid distribution methods", NOT a bad method name.**
  Wasted attempts trying `app-store` vs `app-store-connect`; the name was never the problem.
- Fix: `SKIP_INSTALL: YES` on the watch target (it ships embedded at `AIPedometer.app/Watch/`).
  Verified after: one app under Products/Applications, watch still embedded, ApplicationProperties present.
- **This blocked every App Store/TestFlight export this project could ever attempt.**
