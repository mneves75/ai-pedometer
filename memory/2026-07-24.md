### The one real finding (MEDIUM, from Codex) — fail-closed gap

- Premium smart reminders (`UNCalendarNotificationTrigger`, `repeats: true`) survived entitlement
  revocation because `enforceSmartReminderAccessIfNeeded` only ran as `.task(id:)` on `SettingsView`.
  Subscription expires while Settings is closed → repeating notification keeps firing and
  `smartRemindersEnabled` stays true until the user reopens Settings.
- Fix reused what already existed: the pure decision fn `SettingsSideEffects.smartReminderAccessDecision`
  was fine; only the decision→side-effect mapping was trapped in the view. Extracted
  `SettingsSideEffects.enforceSmartReminderAccess(...)` and drove it at app scope.

### !! My first version of the fix was WRONG — autoreview caught it before commit

- v1 hung enforcement off `AppLifecycleCoordinator` as a foreground hook. `codex exec` review of my
  own uncommitted diff returned **2 mediums against my change**, both verified true in source:
  1. **It would disable PAYING users' reminders.** `canAccessAIFeatures` → `isPremiumActive` → false
     whenever `customerInfo == nil`, which includes the RevenueCat cold-launch resolution window.
     v1 read that as revocation and permanently turned the setting off.
     **Smoking gun: `PremiumAccessStore.isResolvingAccess` (line 172) EXISTS precisely to distinguish
     "not premium" from "still resolving" — and v1 ignored it.** Exactly the MEMORY.md failure mode:
     a "fix" that introduces a worse bug (harms paying customers) than the one it closes.
  2. **It could still miss the revocation.** The coordinator never awaits `PremiumAccessStore.refresh()`
     and stream publications didn't re-run enforcement → could read stale-active state, return `.keep`,
     leave the repeating notification scheduled.
- v2 (also reverted): 3 `.task(id:)` modifiers on the always-mounted root, guarded by `isResolvingAccess`.
  A second independent adversarial review (Claude opus; codex quota was exhausted — logged blocker) found
  the guard INCOMPLETE and proved it in source: `isResolvingAccess` returns **false** for
  `state == .unavailable` (line 181), and `refresh()` sets `.unavailable` with `customerInfo == nil` on
  ANY cold-launch fetch failure (lines 289-290) or verification failure. So a paying subscriber launching
  **offline** hits `isResolvingAccess == false` AND `canAccessAIFeatures == false` → reminders cancelled
  + setting erased, automatically, every offline launch. Same harm class as v1, now with no user action.
  Also flagged: transient `.modelNotReady` (Apple Intelligence assets downloading) as a 2nd destructive
  trigger, and an unresolved mechanism question — whether `.task(id:)` reliably re-fires when ids are read
  at `WindowGroup`-content (Scene) scope vs View-body scope. If not, the whole fix is a silent no-op.

### DECISION: stopped after 2 attempts; escalated to user rather than iterating a 3rd time

- Pattern = signal: 3 review rounds, 3 distinct ways to harm PAYING customers. Root cause: "user is not
  entitled" and "we cannot determine entitlement right now" are **value-identical** at every call site,
  and the store's own resolving helper doesn't cover the failure states.
- Closing it correctly requires 2 PRODUCT/REVENUE decisions, not engineering ones:
  1. When entitlement is undeterminable (offline / RevenueCat unreachable / verification failed): keep
     reminders (favor paying user, small leak to lapsed users) or cancel (strict, penalizes offline subs)?
  2. Should enforcement DESTROY the persisted `smartRemindersEnabled` preference at all, or only cancel
     the pending notification and leave the preference so it resumes when access returns?
- Governing precedent already in MEMORY.md: RevenueCat behavior is revenue-affecting → escalate, don't
  change autonomously (same reason `.informational` vs `.enforced` was escalated).
- **Recommended design (documented in implementation-notes.html, NOT implemented):** act only on
  AUTHORITATIVE evidence of no entitlement (RevenueCat reachable + customerInfo fetched + verification
  passed + entitlement inactive); defer in every other state. Drive from deterministic points (right
  after `premiumAccessStore.prepare()` in the launch sequence + existing `scenePhase == .active`) instead
  of Scene-scope `.task(id:)`, sidestepping the Observation question. Scope to PREMIUM only; leave
  transient AI-availability handling in Settings where the user is present and gets an alert.

### What actually landed (protective-only)

- `smartReminderAccessDecision` gained `isResolvingAccess` (default `false` → all existing callers/tests
  unaffected); SettingsView passes `premiumAccessStore.isResolvingAccess`. **Protective-only: can prevent
  a cancellation, never cause one** → cannot regress fail-closed posture in any state.
- Teeth proven: removing the guard turns exactly the new tests red, incl. `(cancelled → 1) == 0` and
  `(persistedDisabled → 1) == 0` — literally demonstrating the paying-user harm. 11 others stay green.
- Known remaining gap documented: guard doesn't cover `.unavailable`, so Settings mounted during an
  offline launch can still disable. Part of the escalated product decision.
- **LESSON (durable):** severity-inflation cuts both ways. Reviewers over-report on EXISTING code, but
  independent review of the agent's OWN uncommitted diff earned its keep TWICE — catching customer-harming
  regressions the full 612-test suite passed cleanly, because nothing exercised the unresolved-access
  window until a test was written for it. Reviewing your own new code is a different activity from
  auditing old code, with a much better hit rate. Always autoreview own diff before commit.
- **LESSON (durable):** when successive fixes to the same seam each introduce a worse bug, stop and
  question whether the underlying decision is a product call, not an engineering one.

### Mistake/flake log

- First targeted run reported `** TEST FAILED **` — but the cause was `Mach error -308 (ipc/mig)
  server died`, a **simulator-server crash** under contention (I had 3 sim-touching jobs at once),
  with ZERO compile errors and no test case ever executing. Per the documented rule: isolated re-run
  on a clean sim, not a "fix". It passed. **Lesson reinforced: read the failure line before reacting;
  `TEST FAILED` is not automatically a code failure.**
- Operational note: do not run a full E2E, a targeted test run, and a polling wait-loop against
  simulators concurrently — that contention is what killed the sim server.
- **Second, DIFFERENT flake — root-caused and fixed (test-only):**
  `SettingsSideEffectsTests.goalPersistenceDoesNotAwaitRefresh` failed in a full-suite run (613 tests,
  1 issue) but passed **15/15** isolated under `-test-iterations 15 -run-tests-until-failure` → load-
  dependent, not a regression (it's a pre-existing test I didn't touch).
  Mechanism: it did `releaseRefresh.signal(); await Task.yield(); #expect(refreshFinished)`. A single
  `Task.yield()` only guarantees the CURRENT task suspends once — NOT that the released task runs to
  completion. Under load the assertion won the race.
  Fix: explicit `refreshCompleted` latch signalled by the refresh closure; `await refreshCompleted.wait()`
  instead of `Task.yield()`. Assertion NOT weakened — the real contract (persistence returns BEFORE the
  refresh finishes) is still asserted at the same point. Same pattern as the 2026-07-21 StreamRenderProbe fix.
  **Rule of thumb: `await Task.yield()` is never a synchronization primitive in a test. Wait on a signal.**
- **MY MISTAKE — deleted tracked files while "cleaning scratch":** ran `rm -f .supergoal/*.md` assuming
  `.supergoal/` was my own working dir. It is NOT: `.supergoal/PROTOCOL.md`, `ROADMAP.md`, and `STATE.md`
  are **tracked files committed by a previous supergoal run**. `git status` immediately showed ` D` on
  three tracked paths. Restored byte-identical via `git show HEAD:<path> > <path>` (verified
  `git diff HEAD -- .supergoal/` empty). Note: `git checkout HEAD -- <paths>` was correctly BLOCKED by the
  dcg guard as working-tree-overwriting; the `git show` form is the safe restore when the file is *deleted*
  (nothing to clobber).
  **Rule: before any `rm` on a directory, run `git ls-files <dir>` to see what is tracked. Never assume a
  dot-directory is agent scratch just because an agent writes there.**
